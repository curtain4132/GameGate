# 跨平台复古游戏平台：开源项目调研与开发参考

- 整理日期：2026-11-02
- 文档类型：技术选型参考
- 面向读者：产品负责人、客户端与模拟器接入开发者
- 当前状态：已确定基于 RetroArch 二次开发，接受 GPL-3.0 开源分发；具体首版范围和界面方案待确认。
- 决策更新：2026-11-02，用户明确停止追加上游通用验证，开始二开；不考虑 Rust，沿用 C／C++ 生态。下文候选分析保留为调研时的比较记录，不代表仍需重新选择底座。

## 1. 产品背景与已确认边界

建设跨平台复古游戏平台，目标覆盖 Android、iOS／iPadOS、原生鸿蒙、Windows、Linux、macOS。

已确认要求：

1. 游戏只能在 App 内运行，不提供跳转外部模拟器的模式。
2. App 统一提供游戏库、运行入口、游玩菜单、输入配置及存档管理体验。
3. 模拟器通过核心插件接入，初期优先支持老主机平台。
4. 游戏目录与下载地址由第三方游戏源提供，支持用户配置资源源。
5. 尽量将模拟器和游戏文件托管交给第三方，项目维护客户端、接口及兼容能力。
6. 下载内容、核心、存档和设置可保存在用户设备上；官方不托管不代表本地不保存。

尚未确定：

- 受限平台是否接受核心随 App 安装包发布。此前提出过建议，但用户尚未确认。
- 六端首发顺序、首批主机平台与核心名单。
- 商业化方式、发行渠道及各模拟器核心的许可审查。基于 RetroArch 的 GPL-3.0 开源分发义务已接受。

应用内运行可以统一交互，但不能自动保证各核心具有相同的性能、兼容性和功能，需要建立能力声明与兼容性验证机制。

## 2. 调研结论

**优先研究 RetroArch／Libretro 生态作为运行层基础。**

RetroArch 已具备应用内运行多个模拟器核心的主体能力。Lemuroid 适合参考 Android 简化体验；EmulatorJS 可作为 WebAssembly 路线候选；Provenance 和 OpenEmu 适合研究苹果生态实现。

本次未确认存在一个成熟项目，直接完整满足“六端原生支持（含原生鸿蒙）＋第三方游戏源＋模拟器核心插件安装＋统一游戏平台体验”。

建议复用现有模拟器核心与接口生态，重点开发：游戏源协议、核心包管理、兼容性规则和游戏平台交互。

## 4. 重点候选分析

### 4.1 RetroArch／Libretro：运行层首选研究对象

- 仓库：https://github.com/libretro/RetroArch
- 主要语言：C
- 主程序许可证：GPL-3.0
- 本次查询的最近推送：2026-11-02
- GitHub Releases 查询返回的最近发布：v1.22.2，2025-11-20

概念区分：

| 概念 | 职责 |
|---|---|
| Libretro 接口 | 定义核心与宿主之间的调用及数据交换 |
| Libretro 核心 | 实际模拟主机并执行游戏 |
| RetroArch | 实现接口、驱动核心并管理输入与音视频的完整应用 |

RetroArch 虽常被称为前端，但具备应用内运行核心的能力，符合不跳转外部模拟器的要求。

可研究多核心接入、统一输入、音视频驱动、存档、即时存档及核心选项。部分平台和发行版本提供核心获取与更新能力，不能据此外推所有渠道都允许动态下载原生核心。

| 复用路线 | 优势 | 成本 |
|---|---|---|
| 基于 RetroArch 二次开发 | 已有运行功能较完整 | 需熟悉较大的 C 工程，评估界面改造和游戏源接入成本 |
| 自建 App，接入 Libretro 核心 | 产品交互和源模型更自由 | 仍需实现或复用音视频、输入、运行循环及生命周期等宿主能力 |

建议：优先评估 Libretro 接口与核心生态，将 RetroArch 保留为参考实现及二次开发候选，通过原型比较后决定。

许可证需要分层核查。RetroArch、桥接库、各模拟器核心和素材可能采用不同许可证；使用 Libretro 接口不代表可以忽略核心的许可条件。

### 4.2 Lemuroid／LibretroDroid：Android 体验与接入参考

- Lemuroid：https://github.com/Swordfish90/Lemuroid
- LibretroDroid：https://github.com/Swordfish90/LibretroDroid
- Lemuroid 主要语言：Kotlin
- GitHub Releases 查询返回的最近发布：1.17.0，2026-04-21

Lemuroid 说明其基于 Libretro，并集成 LibretroDroid，重点是易用性、Android 集成和用户体验。

项目说明列出的能力：

- ROM 扫描与索引；
- 自动保存和恢复状态、快速保存与读取；
- 优化的触控及可调整的虚拟按键；
- 手柄、Android TV、本地多人支持；
- 云存档同步。

建议用 Lemuroid 研究游戏库、默认配置及游玩流程，用 LibretroDroid 研究 Android 核心桥接。

限制：不能直接外推为六端支持。LibretroDroid 本次仅作为关联候选发现，尚未独立完成 API、维护状态、依赖和许可证核查；直接复用前须补齐。

### 4.3 EmulatorJS：WebAssembly 路线候选

- 仓库：https://github.com/EmulatorJS/EmulatorJS
- 主要语言：JavaScript
- 许可证：GPL-3.0
- 本次查询的最近推送：2026-10-21

项目定位为可集成的库／插件，支持多种老主机与街机系统，提供资源加载配置及 Stable、Latest、Nightly 通道。

可能的组合：

> App 游戏库和源管理 → App 内 WebView → EmulatorJS → 模拟器核心。

该方式仍属于 App 内游玩。可以复用 Web 界面及部分运行逻辑，但必须验证：

1. 各端 WebView 的 WebAssembly、图形、音频、手柄能力。
2. 输入延迟、帧率、耗电和温升。
3. 核心与游戏离线缓存、存档持久化和清理规则。
4. 前后台切换、中断、系统回收及恢复行为。
5. 平台与发行渠道对执行内容和远程资源的要求。

建议针对 FC、GB、GBA 等进行对照原型，不预先承诺六端兼容。项目说明不建议将 Nightly 用于生产。

### 4.4 Provenance：苹果端多核心参考

- 仓库：https://github.com/Provenance-Emu/Provenance
- 仓库描述主要面向 iOS／tvOS；苹果其他平台具体支持范围需逐项确认。

适合研究苹果设备上的多核心组织、游戏库、触控、手柄、存档及生命周期处理。

本次只完成仓库发现和基础元数据核查，未完成构建、许可审查或发行验证，不应直接作为六端通用底座。

### 4.5 OpenEmu：桌面游戏库与插件体验参考

- 仓库：https://github.com/OpenEmu/OpenEmu
- 主要面向 macOS。

适合研究多模拟器游戏库、核心插件管理、控制器配置及桌面体验。不能推断其代码可低成本移植到手机或鸿蒙。

本次只完成仓库发现和基础元数据核查，具体接口、许可证和维护活跃度需继续确认。

### 4.6 RomM：游戏库与元数据参考

- 仓库：https://github.com/rommapp/romm
- 定位：自托管 ROM 管理与游玩平台。

适合研究游戏目录、元数据、封面及个人游戏库。其自托管模式与目标的第三方源客户端模式不同。

建议优先借鉴信息模型与交互，不默认引入完整后端。运行集成、许可证及部署依赖尚未深挖。

### 4.7 harmonyos-libretro-emulator：鸿蒙研究线索

- 仓库：https://github.com/daugf2527/harmonyos-libretro-emulator
- 仓库描述：ArkTS + C++ + XComponent，GLES／Vulkan，多核心 ROM 加载、音频桥接和输入路由。
- 本次查询的最近推送：2026-07-07。
- GitHub 许可证识别：NOASSERTION。

仓库描述与原生鸿蒙需求相关，但规模较小，不能凭描述认定成熟可用。

本次未成功取得可阅读的许可正文。NOASSERTION 仅表示 GitHub 未给出明确的标准许可识别，既不等于没有许可证，也不等于允许复制、修改和分发。

当前仅列为技术研究线索。复用前需阅读许可、检查构建与核心来源，并在目标设备验证渲染、音频、输入和稳定性。

## 5. 第三方游戏源机制的补充参考

运行生态解决如何执行游戏；以下项目用于研究内容如何接入，两类参考分别使用。

| 项目 | 参考方向 | 限制 |
|---|---|---|
| [VeneraNext](https://github.com/CyrilPeng/Venera-Next) | 本体与第三方源扩展分离、跨平台内容管理 | 已读取说明保留 JavaScript 源扩展，漫画接口不能原样作为游戏协议 |
| [Legado](https://github.com/LegadoTeam/legado) | 书源配置、内容聚合思路 | 未深入验证接口与沙箱实现 |
| [LX Music 移动版](https://github.com/lyswhut/lx-music-mobile) | 自定义源返回内容地址 | 移动仓库说明支持 Android，非六端支持依据 |
| [TVBoxOSC](https://github.com/j4Uq/TVBoxOSC) | 内容源入口与聚合交互 | 本次取得说明有限，未验证接口复用可行性 |

扩展建议分别定义：

- 游戏源扩展：目录、搜索、详情、资源地址、元数据。
- 核心插件：实际执行能力、平台架构、核心版本、支持格式、能力声明。

游戏主要关联主机平台、版本和内容标识，由平台选择兼容核心，避免永久绑定单一模拟器。

## 7. 开发前验证清单

### 运行与体验

- 选取少量主机平台和合法测试 ROM，固定版本与校验值。
- 验证所有游戏均在 App 内运行。
- 验证画面、音频、触控、键盘、手柄、暂停与退出。
- 区分游戏内存档与即时存档，记录游戏、核心、版本。
- 验证断网启动、应用重启、前后台切换与系统中断。
- 按核心能力展示即时存档、倒带等可选功能。

### 核心与资源源

- 明确接口版本、系统、CPU 架构、最低宿主版本与 BIOS 要求。
- 分别定义游戏源协议和核心包清单。
- 下载前判断兼容性，下载后校验完整性与发布者来源。
- 验证更新回退、存档兼容、卸载数据保留及下载失败恢复。
- 确认受限平台是否接受随包核心；该产品决策仍待确认。

### 开源与维护

- 分别阅读主程序、桥接库、核心与素材的许可证。
- 检查提交、发布、关键 Issue 和维护者响应。
- 测量包体、核心体积、依赖与构建成本。
- 固定复用版本或提交，记录修改和上游同步方式。
- 原型与实机通过后，再承诺目标端覆盖与性能。
